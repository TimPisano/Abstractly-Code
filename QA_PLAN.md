## Two bugs already found during recon (static read, to be confirmed with a failing test before fixing)

1. **Unit-designator mismatch in address matching.** `rent_roll_import.py`
   only prepends `"Suite "` to a bare unit identifier
   (`_UNIT_DESIGNATOR_RE`); a cell already carrying its own designator
   ("Apt 104", "#104", "Unit 104") is used *verbatim*. Matching in
   `deal_mismatch.py`/`portfolio.py` (`_normalize_address` ->
   `_normalize_for_matching`) only lowercases + strips punctuation — it
   does **not** canonicalize "Apt"/"Unit"/"#" to "Suite". So the same
   physical unit written as "104" (-> "...Suite 104") and "Apt 104"
   (-> "...Apt 104") normalize to two different strings and silently fail
   to match (shows up as a false `unit_no_lease` + `lease_no_unit` pair
   instead of a real comparison). This is exactly item 2's "units written
   differently" case. Needs a reproducing test against the real import +
   match pipeline before touching code.
2. **Test-isolation bug (pre-existing, not introduced by me).**
   `tests/test_pms_synthetic_fixtures.py::test_synthetic_fixtures_round_trip_through_the_real_import_route`
   never calls `database.configure()`/`init_db()` itself (every sibling
   `*_api.py` test does, via a `_fresh_temp_db()`-style helper). It relies
   on ambient global DB-path state left over from whichever test ran
   before it in the same pytest process. When that leftover path is a
   deleted tempfile, SQLite silently recreates an empty file with no
   schema -> `OperationalError: no such table: leases`. Reproduced: passes
   alone, fails in the full 870-test run (confirmed in baseline, see
   below). Fix: give it its own isolated temp DB + `init_db()`, matching
   the established convention.

Also confirmed by direct reading (not trusting a first-pass summary) that
match detectors do a full cross-product within an address group
(`detect_rent_mismatch` et al. loop `for rr_lease ... for doc_lease ...`),
so duplicate rent-roll rows or multiple leases for the same unit will
multiply findings rather than dedupe — relevant to item 2's "duplicate
units" and "multiple tenants per unit" cases. To confirm with a test, not
assumed a bug yet — may be reasonable given only one is normally present.
